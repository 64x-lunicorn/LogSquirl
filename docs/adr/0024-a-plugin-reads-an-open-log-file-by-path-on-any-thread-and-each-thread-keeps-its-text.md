# A plugin reads an open Log File by path on any thread, and each thread keeps its text

A plugin could read only the Log Lines selected in the tab in front, on the UI thread, at most 1000 of them and 1 MiB (#663). A plugin that analyses a whole Log File opened the file itself: it then had to read it in the right encoding (#803), it read the original bytes of a converted or decompressed Log File rather than the text LogSquirl shows, and its line numbers could disagree with the views'. It heard of the active file and of encoding changes, but not of Log Lines appended, of a reload or of a truncation. An analysis of a large Log File belongs on a thread of the plugin's own, and the only lookup the Plugin Host had -- the tab in front, through callbacks the UI sets -- works on the UI thread only, since a worker that waits for the UI thread while the UI thread waits for it deadlocks (#858).

## Decision

- **Three host functions are appended** (ADR 0017), all LogSquirl 26.12: `get_log_line_count`, `get_log_lines` and `register_log_lines_callback`. They answer with the `LogSquirlLogLinesResult` codes; no new code was needed. `get_log_lines` returns what `get_selected_log_lines` returns, under the same bounds: UTF-8 decoded as the views show it, `'\n'`-separated, NUL-terminated, whole Log Lines up to `LOGSQUIRL_SELECTED_LOG_LINES_MAX_LINES` and `LOGSQUIRL_SELECTED_LOG_LINES_MAX_BYTES`, a first one longer than that cut at a character, `TRUNCATED` when fewer than asked for and than there are fit. Log Lines are numbered from 1, as the views and `go_to_log_line` number them.
- **The Log File is named by its path**, the path `get_active_file_path` and the active-file callback give, and matched as the file system names a file, as `get_log_file_encoding` matches it: any tab of any window, in front or not. A path no tab shows gives `NO_LOG_FILE`.
- **The Plugin Host keeps the open Log Files itself, in a list it looks up without the UI thread** (`PluginLogFiles`). The UI adds each tab's Log File when the tab opens -- a source over its log data, which LogData already reads safely from any thread for the Searches -- and removes it when the tab closes. A lookup copies the list under a lock and compares outside it. It is shared by every plugin function that names an open Log File, so the later ones (#866, #867) find a Log File the same way.
- **What a lookup finds is held for the call.** The list hands out shared holds; removing a Log File marks it no longer open. A read under way when its tab closes finishes on the data it holds, and then answers `NO_LOG_FILE`, as one that came after. The read never blocks the tab from closing, and the views never wait for a plugin. A hold that a plugin's thread lets go last hands the log data back to the UI thread to be destroyed there, since it is an object of that thread's.
- **The text of `get_log_lines` is per plugin and per thread**: valid until the same plugin calls `get_log_lines` again on the same thread, or is shut down. This narrows ADR 0022's rule -- until the same plugin calls the same function again -- for a function made to be called on several threads at once: one buffer per plugin would be overwritten by another of its threads under the first one's reading. The buffers live in the plugin's context, one per thread id, until the plugin is unloaded.
- **One change callback per plugin**, replaced by a second registration and removed by `NULL` (ADR 0022). It is called on the UI thread with the path, the count after the change and one of two changes: `LOGSQUIRL_LOG_LINES_APPENDED` when a load only added Log Lines at the end -- what was read stays, but for the last Log Line, which may have grown -- and `LOGSQUIRL_LOG_LINES_REPLACED` for every other load -- the first one, a reload, one after a truncation -- and when the Log File reads differently, in another encoding or under another Decoding Policy. The first load counts as a replacement: the encoding is detected only once it has read the file, so what a plugin read while it ran may decode differently. Calls may be coalesced, though the host does not yet.

## Considered Options

- **Naming the Log File by the tab in front, or by an id the host hands out.** The tab in front is a UI-thread notion and changes under a worker; an id would need a way to learn it, and every other function names a Log File by its path.
- **Dispatching the read to the UI thread with a blocking call.** It is what `get_active_file_path` refuses for its deadlock; it would also stall the views for every block a plugin reads.
- **One buffer per plugin, as for every other returned string.** Two threads of a plugin would overwrite each other's text; a plugin would have to serialise its own reads, which defeats reading on threads. A buffer the plugin passes in would avoid host-owned text altogether, but every other function returns host-owned text, and a plugin would have to guess the size.
- **Waiting, as the tab closes, for the reads under way.** Each read is bounded, but a slow disk would stall the UI thread for it; the shared hold lets the tab close at once.
- **Appending the first load.** Simpler for a plugin that reads while the Log File loads, but wrong whenever the detected encoding differs from the one the load began in.

## Consequences

- A plugin reads any open Log File, converted and decompressed ones included, as LogSquirl shows it, on whichever thread it likes, and hears when to read on or read again.
- A plugin that calls `get_log_lines` from many short-lived threads keeps one buffer of up to 1 MiB for each, until it is unloaded; a thread that reuses an ended thread's id reuses its buffer.
- A Log File stays readable by a plugin's read already under way after its tab closed, until that read returns; the read's result says it is gone.
- Marks (#866) and the fields of Log Lines (#867) by path look the Log File up the same way and keep their text the same way; a field read that depends on the Log Format tells a changed Log Format through the same callback, as a replacement.
