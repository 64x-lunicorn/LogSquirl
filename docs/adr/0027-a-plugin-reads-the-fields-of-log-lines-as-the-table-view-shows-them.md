# A plugin reads the fields of Log Lines as the Table View shows them

A plugin that analyses a structured Log File -- statistics per level, per component, per request -- read its Log Lines as text (ADR 0024) and had to parse them itself: with a parser of its own that disagreed with the Log Format LogSquirl applied, and knowing nothing of the Log Format Format Recognition chose, or of a change of it (#867, part of the decision in #860). LogSquirl computes the fields of a Log Line in one place, `TableRowCells` over the Log Format, which the Table View's cells, the exports and the Field Terms of a Search (`LogFormatFieldReader`) all read, so they cannot drift apart.

## Decision

- **Two host functions are appended** (ADR 0017), both LogSquirl 26.12: `get_log_format_fields` names the Log Format that applies to an open Log File and its fields; `get_log_line_fields` reads the fields of a range of its Log Lines. They follow `get_log_lines`: the Log File by its path, found through `PluginLogFiles`; Log Lines numbered from 1; any thread, never waiting for the UI thread; the same caps, `LOGSQUIRL_SELECTED_LOG_LINES_MAX_LINES` Log Lines and `LOGSQUIRL_SELECTED_LOG_LINES_MAX_BYTES` bytes, here of the values together; `TRUNCATED` when fewer Log Lines than asked for and than there are fit.
- **One result code is appended**: `LOGSQUIRL_LOG_LINES_NO_LOG_FORMAT` (-6), for a Log File no Log Format applies to. An enum constant appended changes no size; an older host never returns it.
- **The fields are those of the Table View's columns, in their order, named as their headers, without the elapsed time**, which is computed from neighbouring Log Lines and is no field of the Log Format. The name is the Log Format's own (the key of its definition), not its title, since that is what a plugin shipping Log Formats (`formats`) knows it by.
- **The values are read through `LogFormatFieldReader`**, the reader the Field Terms use, over the Log Format the tab's Table View shows: what it gives is what `TableRowCells` puts in the cells. A Log Line the Log Format does not parse -- a regex Log Format that does not match it, one the regex engine gave up on, one longer than a Log Format parses -- has no fields, as a Field Term treats it, though the Table View shows it whole in its last column. A JSON or logfmt Log Format parses every Log Line, and one that is no JSON object has every field empty, as the Table View shows it.
- **Out-parameters, row-major**: an array of `field_count * line_count` pointers to the values, an array of as many lengths, and an array of `line_count` flags, 1 for a Log Line parsed and 0 for one not; a Log Line not parsed has `NULL` values of length 0. A value is UTF-8 and NUL-terminated for convenience, but read by its length: it may hold a tab, a line feed or a NUL. `field_count` comes with the values, so a plugin sees when the read was under another Log Format than the names it holds.
- **The bytes cut whole Log Lines**, as `get_log_lines` does: the values of a first Log Line longer than the bound are cut, the value that passes it at a character and those after it empty.
- **The arrays, names and values are per plugin and per thread** (ADR 0024): a `PerThread` buffer of each kind in the plugin's context, valid until the same plugin calls the same function again on the same thread, or is unloaded.
- **Each tab keeps the Log Format it shows for the plugins in an object of its own (`LogFormatForPlugins`)**, under a lock, holding the `LogFormatFieldReader` built once per Log Format. The tab sets it as a load finishes, after the Table View was brought up to date; a read takes the one set as it starts and keeps it to its end. Each Log Line is read up to 4 MB: a character takes at most 4 bytes, so one cut there has more characters than a Log Format parses (`MaxUiThreadLineLength`).
- **Another Log Format, or none, is a replacement**: the change callback of ADR 0024 reports `LOGSQUIRL_LOG_LINES_REPLACED` when a load finishes under another Log Format than before, though the load only appended Log Lines -- as when Format Recognition finds one as a Log File too short for one grows. Every other change of Log Format comes with a load from the start (a reload, a truncation), which is a replacement already. LogSquirl has no choice of Log Format by the user yet; one would go through the same point.

## Considered Options

- **Reading the Table View's model.** It lives on the UI thread, caches only what was painted, and a tab whose Table View is hidden or sorted has its Rows elsewhere; a worker cannot read it without waiting for the UI thread.
- **Including the elapsed column as a field.** It is the Table View's, not the Log Format's; a plugin computes it from the timestamp field if it wants it, and a Field Term cannot name it either.
- **The Table View's last cell for a Log Line not parsed.** It shows the raw Log Line there for the user; a plugin computing statistics per field would count it as a value of that field. A Field Term matches nothing of it, and `get_log_lines` gives its text.
- **A struct of out-parameters**, or a buffer the plugin passes in. A struct would need its own size member to grow; a buffer the plugin passes would make it guess sizes; every other function returns host-owned memory.
- **Returning the field names with every read** instead of `field_count`. Cheaper to check a count; a plugin reads the names again on `REPLACED`, which comes after every change of Log Format.
- **Reading each Log Line whole.** What the Table View does, but unbounded: a plugin reading a Log File through would read a single huge Log Line whole, where the Log Format parses no Log Line past a million characters anyway.

## Consequences

- A plugin computes statistics over the fields of a structured Log File on a thread of its own, with the values the user sees in the Table View, and reads them again when the change callback says the Log Lines were replaced.
- A read that runs while the Log Format changes may be under either; the callback that follows tells the plugin to read again, as for a reload during a read of Log Lines.
- A Log Line of more than 4 MB whose text is under a million characters -- one of mostly hidden ANSI color sequences, say -- is not parsed for a plugin, where the Table View may parse it.
- A plugin that calls the two functions from many short-lived threads keeps one set of buffers for each, until it is unloaded.
