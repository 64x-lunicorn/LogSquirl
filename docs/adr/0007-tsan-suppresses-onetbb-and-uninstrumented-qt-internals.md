# TSan suppresses oneTBB's flow graph and one uninstrumented-Qt finding

The suppressions this decision made were removed by #482, and the job that runs TSan over the whole suite now blocks; see the update at the end, which supersedes the Decision below where they differ.

#331 needed "the TSan build of the search tests passes", which could not be satisfied as it stood: measured against `-DENABLE_SANITIZER_THREAD=ON` (`cmake/Sanitizers.cmake`), RelWithDebInfo, LTO off, the base commit (0845ff22) already failed 9 of 23 ctest cases, and #331's own change added a 24th failure that reports no new race — only the same 9 pre-existing findings plus one more report of them. Every one of those findings is in code TSan cannot instrument:

- **oneTBB's flow graph** (used by indexing and by the search pipeline): `graph_task`, `input_node_task_bypass`, `forward_task_bypass`, and vptr races on TBB-allocated tasks. TBB's flow graph is deliberately not a clean virtual hierarchy (see the UBSan `-fno-sanitize=vptr` comment in `cmake/Sanitizers.cmake` for the placement-construction/`static_cast` pattern this comes from) and its internal small-object pool and spin-locks are not fully visible to TSan's happens-before model in the CPM-vendored build LogSquirl links. oneTBB ships its own `cmake/suppressions/tsan.suppressions` upstream for the same subsystem, which this suppression list mirrors in shape.
- **`QThreadPoolThread::run()`** in uninstrumented QtCore, reported as a race on the `shared_ptr<const RegularExpression>` that `LogFilteredDataWorker::search()` captures into the runnable it queues.

With a local suppression file (`race:tbb::detail::`, `race:tbb::flow`) the issue's own measurement reported failures dropping to 3-5, before and after #331's change alike.

Re-measured in this session, on a from-scratch `-DENABLE_SANITIZER_THREAD=ON -DCMAKE_BUILD_TYPE=RelWithDebInfo -DENABLE_LTO=OFF` build with `cmake/tsan.supp` applied via `TSAN_OPTIONS`: every scenario in the two clusters that actually exercise `LogFilteredDataWorker`'s search path — the 14 `SearchSession` scenarios (`tests/unit/searchsession_test.cpp`, ctest #308-321) and the 63-scenario `logsquirl_itests` cluster covering search, deadlock-on-destruction and TBB-worker-exhaustion behaviour (ctest #445-507) — **passed clean, 77/77**, with no remaining findings. This is a from-scratch measurement made for this ADR, not a re-quote of the issue's own numbers; it does not reproduce the issue's exact "23" denominator (that count's originating test selection was not written down and could not be reconstructed exactly), but it directly answers the acceptance criterion by running every test that plausibly counts as "the search tests" and finding none of them fail under the suppressions.

## The `shared_ptr<const RegularExpression>` finding, examined on its own merits

This one is not suppressed reflexively. Reading `LogFilteredDataWorker::search()` and `updateSearch()` (`src/logdata/src/logfiltereddataworker.cpp`):

1. `compiledExpression` arrives by value (a copy already), and the lambda queued with `operationsPool_.start(createRunnable(...))` captures it **by value again** (`[ ..., compiledExpression, ... ]`, not by reference).
2. That copy is moved once more into `SearchOperation::compiledExpression_`, which is `const` and never reassigned — the pool thread only ever *reads* through it (`matcher.hasMatch(line)` and friends) once the search runs. Nothing mutates the pointee or the pointer after the runnable is queued.
3. The calling thread's own copy (the `search()`/`updateSearch()` parameter) goes out of scope when the function returns, on whichever thread called it — concurrently, in general, with the pool thread later destroying its own copy when the runnable finishes.

So the actual concurrent operation is: two `std::shared_ptr` copies of the same control block being destroyed (decrementing the refcount) on two different threads with no explicit lock between them. That is exactly the case `std::shared_ptr` is specified to make safe on its own: the control block's refcount operations are atomic (or use an equivalent synchronized path) regardless of whether the surrounding code takes a mutex. It does not depend on `QThreadPool`'s internal handoff being visible to TSan — it would be safe even if the two threads had no other synchronization at all.

TSan flags it anyway because `QThreadPoolThread::run()` lives in Qt's own binary, built without `-fsanitize=thread`. Qt's queue hand-off (a mutex/condvar internally) is a real happens-before edge, but an instrumented and an uninstrumented thread meeting inside an uninstrumented library leaves TSan unable to see that edge, so it falls back to reporting the two instrumented touches of the shared control block (the constructor call in `search()`/`updateSearch()` and the destructor call once the runnable completes) as unsynchronized.

**Conclusion: this is a TSan blind spot on uninstrumented Qt internals, not a real race.** The suppression for `QThreadPoolThread::run` / `QThreadPool::start` in `cmake/tsan.supp` reflects that judgment, not an unexamined "make it quiet" suppression. If `LogFilteredDataWorker::search()` is ever changed to capture the expression by reference, or to mutate the pointee, this reasoning would need to be redone.

## Decision

- `cmake/tsan.supp` lists both classes of finding, each with the reasoning above inline as a comment.
- `cmake/CatchTestDiscoveryRunTest.cmake` sets `TSAN_OPTIONS=suppressions=<repo>/cmake/tsan.supp` on every ctest run unconditionally; the variable is ignored by binaries not built with `-fsanitize=thread`, so this has no effect outside a TSan build.
- BUILD.md documents the same suppression file for anyone running a TSan binary directly, outside ctest.
- Adding a TSan CI job and fixing any *new* race this work might surface beyond what was measured for #331 are both out of scope for this decision (tracked, if needed, as separate issues).

## Consequences

- The search tests themselves — the acceptance criterion this ADR exists to satisfy — pass clean under these suppressions (77/77, see above); no remaining search-test finding needs to be written down, because there isn't one.
- Outside the search tests, the issue's own measurement (9/23 failing on the base commit, dropping to 3-5 with a local suppression file) implies other test areas — most plausibly indexing, which also drives oneTBB's flow graph — still hit findings these two suppression classes don't fully cover. That measurement's exact test selection was not written down and could not be reconstructed in this session, so those specific remaining findings are **not enumerated here**: this ADR's suppressions target what was identified (oneTBB's flow graph broadly, and the one named Qt/`shared_ptr` finding), not a re-run of that exact original count. Anyone hardening the TSan build further than the search tests should expect to find and triage additional oneTBB-adjacent findings outside search, starting from a fresh TSan run rather than assuming a clean baseline everywhere.
- The suppression file is shape-matched, not exhaustive: a new oneTBB symbol outside `tbb::detail::` / `tbb::flow::` or a Qt internal outside `QThreadPool*` will still be reported and needs its own line and its own reasoning, not a blanket widening of an existing pattern.
- A finding in LogSquirl's own hand-off through Qt's event queue is fixed in the code where that is simple, not suppressed. #409 is the example: `FileWatcher::applyWatchPolicy()` queued a lambda to the poll thread with `QMetaObject::invokeMethod( ..., Qt::QueuedConnection )`, and TSan reported the lambda's captures (`this` and two copied policy values), written when Qt built the functor on the UI thread and read when the poll thread ran it. Nothing the main thread writes later was shared: the captures are copies, and `pollWorker_` is set once, in the constructor. So there was no race, only Qt's event-queue hand-off, which TSan cannot see. The polling half of the Policy now goes through a signal connected before the poll thread starts. That carries only copied values, and TSan has nothing to report, so `cmake/tsan.supp` gains no line for it.

## Update (#482): the whole suite, sorted, and the job blocks

The first run of the `Sanitizers / tsan` job over the whole suite (actions run 35983943493) printed 902 `data race` reports and turned 75 of 742 cases red (#482 counted 912 and 78). The run on master after #496 (actions run 36096812787) printed 1059 and turned 80 of 782 red. That second run is what this section sorts. Two things about the CI container come first, because the sections above got them wrong: its Qt is the prebuilt Qt 6.11.2 that aqtinstall puts under `/opt/qt`, not a distribution package, and like every prebuilt Qt it is not built with `-fsanitize=thread` and has no symbols for its internal functions, which show as `<null> (libQt6Core.so.6+0x...)`. And oneTBB, which LogSquirl builds from source, was built without TSan as well.

### Who made the racing accesses

Each report names two accesses. An access counts as made by the module of its first frame after TSan's interceptor frame (`operator new`, `free`, `memcpy`, ...) and after the frames of inlined Qt and C++ standard library headers. Counted that way, the 1059 reports were:

| Racing accesses | Reports | Cases |
| --- | --- | --- |
| both inside QtCore, QtGui or QtNetwork: Qt allocates, frees, copies or reallocates on two threads (posted events and their argument arrays, `QFuture` results, font and image caches, the host lookup, a `QThreadPool`'s `QWaitCondition`) | 957 | 68 |
| both inside glibc: `mktime()` replaces the parsed `TZ` (`strdup`, `free`) from whichever thread converts a time | 54 | 19 |
| both inside GLib: the eventfd a `GMainContext` wakes up through | 5 | 5 |
| QtCore frees a `QString` payload whose reference count LogSquirl's code dropped on another thread a moment before (`logdataworker.cpp:995`, `QArrayData::deref`) | 1 | 1 |
| both in LogSquirl's code: the captures of the runnables `LogFilteredDataWorker::search()` / `updateSearch()` queue, written on the calling thread and read on the pool thread | 42 | 5 |

Not in the table, because the suppression file hid them: the races in oneTBB's flow graphs. The entries `tbb::detail::*` and `tbb::flow::` matched every stack that ran through a flow graph node, the Search's and the indexing's code included. Without them (actions run 36106519277) 2225 reports with oneTBB frames came out of 28 cases, most of them LogSquirl's nodes being torn down after `wait_for_all()` while a TBB worker was still in its epilogue. TSan never printed its list of matched suppressions for them in these runs (why was not found out); the run without the entries is the evidence. The Qt entries `QThreadPoolThread::run` and `QThreadPool::start` could not match anything: those functions have no symbol in the container's Qt.

### What is fixed in the code

- **The runnables' captures.** `RunnableWrapper` (`src/utils/include/runnable_lambda.h`) is built on the thread that queues it and run on a pool thread. `QThreadPool` hands it over under a lock inside QtCore that TSan cannot see, so every capture read on the pool thread raced with its construction. The wrapper now publishes itself: a release store at the end of its constructor, an acquire load before it runs. That is a real edge, costs next to nothing, and covers every runnable of `LogDataWorker` and `LogFilteredDataWorker`. `tests/unit/runnable_lambda_test.cpp` queues a runnable to a pool thread that is already running, the case the Search hit; without the pair it is red under TSan (actions run 36102659877).
- **The `QSemaphore operationStarted`** in `LogFilteredDataWorker::search()` / `updateSearch()` (#496) was captured by reference, so the caller could return from `acquire()` and destroy it while the pool thread was still inside `release()`, the shape of the `GrowingLogData` bug fixed in #476. It is shared now. The `shared_ptr<const RegularExpression>` finding of the first section is one of the capture reports above: the wrapper's edge settles it, not a suppression.
- **The time lookup's job.** `LookupRunner` (#486) handed its worker a raw pointer into the job whose cancel flag the work reads, and the watcher's slot held the only share and let go of it after the result was reported. QFuture orders the two inside QtCore, so TSan reported the free against the worker's last read of the flag (`timelookup.cpp:63`, `A cancelled time lookup leaves no result behind`, once oneTBB was built with TSan and nothing else was left). The worker now holds a share of the job too; the count shows TSan the order QFuture keeps.
- **QuickFind's previous future.** `QuickFind::startSearch()` waits for the previous search, then drops its future, which frees the state the worker reported its result into under the future's lock. The wait orders the two inside QtCore; TSan saw the worker's unlock (Qt's inline, annotated header) and the free on the UI thread with nothing between them (`Scenario: a Filtered View QuickFind runs while Marks change`, timing-dependent, first seen on PR #509). `startSearch()` now reads the finished result before dropping the future; that takes the same lock in Qt's inline code, which TSan sees.
- **Test scripts that start a LogSquirl binary themselves** (`tests/logsquirl_grep_cli.cmake`, `logsquirl_smoke.cmake`, `test_binary_own_settings.cmake`, `version_as_declared.cmake`) went around the runner, so its sorting did not apply to them: a Qt-internal race in `logsquirl_grep` (a queued call's event block, QtCore on both sides) failed `logsquirl_grep_cli` on PR #509. They now use `logsquirl_tsan_prepare()` / `logsquirl_tsan_check()` from `cmake/TsanReportFilter.cmake`, the same rule as the runner.
- **oneTBB is built with TSan** in a TSan build (`TBB_SANITIZE`, oneTBB's own option, in `3rdparty/CMakeLists.txt`). TBB's scheduler then hands work to its workers through atomics TSan sees, and all 2225 flow-graph reports are gone without a suppression. The TSan test run went from 19 to about 7 minutes with it.

### What is left out, and why not with a suppression

The reports of the first three rows are between a library and itself. TSan sees the calls Qt, GLib and glibc make into its interceptors, but not the locks and atomic reference counts inside them that order those calls (`QMutex`, `QAtomic*`, `GMutex` and glibc's own locks are futexes in uninstrumented code). They are not races in LogSquirl, and nothing in LogSquirl can remove them. TSan has no rule for "the racing access was made inside this library", and each rule it has was measured or read against that need:

- **`race:` on a library or on Qt's function names** matches any frame of either stack, callers included. LogSquirl's slots run on top of `QCoreApplicationPrivate::sendPostedEvents`, its runnables on top of `QThreadPoolThread::run`, its indexing on top of oneTBB's flow graph, so such an entry hides races in LogSquirl's own code as well, as the oneTBB entries did. All `race:` entries are removed.
- **`called_from_lib:<library>`** also makes TSan skip the synchronization the library does through its interceptors (`pthread_cond_wait` in `QWaitCondition`, `pthread_join`). With QtCore, QtGui, QtNetwork, GLib and glibc listed, the run printed 4079 reports and turned 160 cases red (actions run 36102659877): races between LogSquirl's own accesses, because TSan no longer saw `QFuture` and `QThread` hand them over.
- **`ignore_noninstrumented_modules=1`** keeps the synchronization, but on Linux TSan marks no module as instrumented, so it ignores every interceptor call, LogSquirl's own `new`, `delete` and `memcpy` included. That is the class of #476 (an object destroyed while another thread is still inside it), which TSan would stop finding.
- **Qt built with `-fsanitize=thread`** would let TSan see Qt's locks and need no rule at all. Unlike oneTBB, Qt is not built with LogSquirl: it means building qtbase (and Qt 5 Compat, Qt SVG, the tools) from source into a second CI image, about an hour on a GitHub runner for every change to that image, a much larger image, and the image signing of #216 extended to it. Worth it if the rule below ever lets a real race through; not for the reports seen here.

So the rule lives in the ctest runner. `cmake/CatchTestDiscoveryRunTest.cmake` has TSan write its reports to files (`log_path`, with `exitcode=0` so the case keeps its own exit code), and `cmake/TsanReportFilter.cmake` sorts them once the case has ended. A data race report is left out only when both racing accesses were made inside a library that `cmake/tsan.supp` lists on an `#@uninstrumented <library>` line, with the reason next to it. Two narrow additions, each with a test:

- An atomic operation inside `QArrayData::ref`/`deref`, the reference count of Qt's implicit sharing, counts as QtCore's even when it is inlined into LogSquirl's binaries: QtCore frees the payload after a decrement TSan does not see there (the fourth row).
- A slot that Qt calls for a queued signal (`QObject::event` in QtCore below it) reading an argument QtCore copied for that call (`QMetaType::create` in QtCore allocating it on the emitting thread): Qt hands the copy over through its event queue, and nothing else holds it. `SearchSession::handleSearchFinished()` reading the error message of `searchFinished` showed this (`searchsession.cpp:446`, in the first run and after oneTBB was built with TSan). The same read against any other allocation still fails the case.

Every other report fails the case, one access in LogSquirl's code being enough, and so does anything else TSan prints (an internal error, a warning about a thread, a report cut off). The case's output ends with lines that count what was left out. `tests/tsan_report_filter.cmake` checks the sorting on reports taken from the CI job, including the cases that must stay.

The price: a race between two accesses that both happen inside Qt's library code, on an object LogSquirl shares between threads without a lock, is left out too, unless one of the accesses is in an inlined Qt header (most of `QString`'s and `QList`'s are). TSan never saw such a race before either, only Qt's calls into its interceptors around it.

### One suppression, in oneTBB

With oneTBB instrumented, TSan found a race in oneTBB itself: `threading_control::set_active_num_workers()` calls `get_threading_control()` without the lock every other caller holds, so it reads the global `threading_control` while a TBB thread that ends drops the last reference and clears it. It is reached when a `tbb::global_control` is destroyed (the case that runs indexing without a TBB worker, and `main()` at exit). Upstream oneTBB takes the lock there; the fork LogSquirl builds (variar/oneTBB c9be1ac) does not. It is suppressed with `race_top:`, which matches only the frame that made the racing access, not its callers, so it cannot hide a race in LogSquirl's code. Moving to a oneTBB with the fix removes the entry.

### Checking that no race in LogSquirl's code is left out

Before (run 36096812787), 43 reports had a racing access in LogSquirl's code by the counting above, at 10 sites: the 42 capture reports (`logfiltereddataworker.cpp` lines 286-324, `runnable_lambda.h:51`, `searchsession.cpp:145`) and `logdataworker.cpp:995`. Run over all 1059 reports of that run, the filter keeps exactly those 42 (fixed, see above) and leaves out 1017, among them the one at `logdataworker.cpp:995` (the reference count row). Over the first run's 899 parsed reports it keeps the same capture sites, the `GrowingLogData` race #476 fixed (`tests/unit/growinglogdata.h`), and nothing else of LogSquirl's; the two `searchsession.cpp:446` reads it leaves out are the queued-argument pair. Of the reports left out in the second run, 882 have LogSquirl's code further down a stack, as the caller that asked Qt or glibc to allocate or free (`WelcomeDashboard` building its widgets, `IconLoader::load` converting a file time, a test's body); none has a racing access there.

### The cases that timed out

- **The two Team Folder cases** (`A Team Folder without Git reports that Git is missing`, `A publish that stops before committing is answered, not lost`) hung; they were not slow. Run alone under TSan with a limit of 600 s (actions run 36102659877), both were still running when they were killed. A backtrace after 75 s showed the Team Folder's worker thread in `QProcess::waitForStarted()`, blocked in a `read()` of 152 bytes (the `pipe_payload` of forkfd's fork fallback), and the child it had forked a zombie. Under a sanitizer Qt does not use its pidfd path (`globalUsingVfork()` finds `__interceptor_vfork` and falls back to `fork()`), and the fallback learns of the child's exit from a SIGCHLD handler; under TSan that wait never returned. It happens only when the program cannot be executed, which both cases arrange on purpose. `Git::run()` now looks a missing program up first, the way QProcess would (`QStandardPaths::findExecutable` for a bare name; an absolute path that does not exist), and reports it without starting a process. Outside TSan that saves a fork; under TSan both cases pass. Windows is left to QProcess: its lookup differs, and it forks nothing.
- **The three `logsquirl_itests` cases** on growing or rewritten Log Files (`An explicit reload notices a Log File rewritten in place with the same size`, `Following a growing Log File reads only what was appended`, `Reopening a grown Log File indexes only what was added to it`) were slow, not hung: they kept indexing until the 120 s limit, one pass over an 11 MiB file taking 15 to 78 s where it takes 50 ms outside TSan. With oneTBB built with TSan they finish in 2 to 7 s and run under TSan like every other case; the cost was TSan working through what it could not see in the uninstrumented oneTBB, not the cases.

### Other red cases

`mimalloc serves malloc only with the process-wide override` expected `mi_malloc()` blocks inside mimalloc's heap region, which fails under TSan as it does under ASan: mimalloc's segment map covers the addresses below 48 TiB and asks for memory at 2 TiB and up, but TSan keeps 1 to 16 TiB for its shadow memory and maps everything far above 48 TiB. The test expects that now. `logsquirl_tests_scrollrepaint_device_pixel_ratio_2` ran its binary without the runner, so without the suppression file and the sorting; it goes through the runner now.

### Consequences

- The `Sanitizers / tsan` job runs for pull requests as well and blocks like `Sanitizers / asan-ubsan`; `continue-on-error` is gone, and no case is excluded from it. #439's "blocking like the ASan/UBSan job" holds.
- A new report fails the case unless both of its accesses are inside a listed library (or it is one of the two narrow patterns above). A library is added to the list only with its reason, after its reports have been read. A report with an access in LogSquirl's code is fixed in the code, as #409 and the runnables were.
- `cmake/tsan.supp` holds no `race:` entry. A `race_top:` entry is allowed for a function that calls no code of LogSquirl's, with its reason and how it goes away.
